## 背景

`file-search` 服务在线上出现 `java.lang.OutOfMemoryError: Java heap space`，GC 日志显示老年代持续上涨且 Full GC 无法回收。排查时从日志中定位到一条高频执行的 SQL：

```
insert into `t_fs_share_file_info` (...)
select ...
from `t_fs_share_file_info`
where `is_deleted` = 0
```

## 根因分析

该 `INSERT ... SELECT` 语句的过滤条件仅包含 `is_deleted = 0`。在业务查询入口，过滤维度（如 `share_id`、`file_id`、`user_id`）被设计为可选参数，前端未传时直接跳过拼装：

```java
Example example = new Example(FsShareFileInfo.class);
Example.Criteria criteria = example.createCriteria();
criteria.andEqualTo("isDeleted", 0);   // 恒存在的兜底条件

if (query.getShareId() != null) {
    criteria.andEqualTo("shareId", query.getShareId());
}
if (query.getFileId() != null) {
    criteria.andEqualTo("fileId", query.getFileId());
}
if (query.getUserId() != null) {
    criteria.andEqualTo("userId", query.getUserId());
}
return mapper.selectByExample(example);
```

当全部过滤参数缺失时，生成的 SQL 等价于 `SELECT ... FROM t_fs_share_file_info WHERE is_deleted = 0`，即**全表扫描**。随着 `t_fs_share_file_info` 行数增长，单条查询即可将数十万至数百万行结果集一次性载入堆内存，触发 OOM。

因此，"校验参数不能为空"在此处的真实作用并非字段约束，而是**保证查询语句始终携带有效的过滤条件，避免退化为无 WHERE 过滤的全表扫描**。

## 修复方案

### 1. 入口参数校验

在 Service 层强制要求至少一个过滤维度非空，否则拒绝执行查询：

```java
public List<FsShareFileInfo> listShareFiles(ShareQueryDTO query) {
    if (query.getShareId() == null
            && query.getFileId() == null
            && query.getUserId() == null) {
        throw new BizException("查询参数不能为空，请至少指定 shareId / fileId / userId 之一");
    }
    // ... 构造带有效条件的查询
}
```

也可在 Controller 层通过 JSR-303 拦截：

```java
public class ShareQueryDTO {
    private String shareId;
    private String fileId;
    private Long   userId;

    @AssertTrue(message = "查询参数不能为空，请至少指定一个过滤条件")
    public boolean isQueryValid() {
        return shareId != null || fileId != null || userId != null;
    }
}
```

### 2. 过滤字段加复合索引

即便参数齐备，若缺少索引仍会触发全表扫描。为高频过滤维度建立 `(维度列, is_deleted)` 复合索引，使常量条件 `is_deleted = 0` 能命中索引：

```sql
ALTER TABLE `t_fs_share_file_info`
  ADD INDEX `idx_share_id` (`share_id`, `is_deleted`),
  ADD INDEX `idx_file_id`  (`file_id`,  `is_deleted`),
  ADD INDEX `idx_user_id` (`user_id`,  `is_deleted`);
```

### 3. 分页 / 行数上限兜底

作为最后一道防线，强制分页或限制返回行数，防止任何遗漏过滤条件的查询在内存中加载全量数据：

```java
Page<FsShareFileInfo> page = new Page<>(1, 1000);
return mapper.selectPage(page, queryWrapper);
```

## 防护层次

| 层次 | 手段 | 防护目标 |
|------|------|----------|
| 入口 | 参数非空校验 | 防止过滤条件缺失导致查询退化为 `WHERE is_deleted = 0` |
| 存储 | 过滤字段复合索引 | 防止带条件但仍走全表扫描（索引缺失） |
| 执行 | 分页 / 行数上限 | 防止漏网查询一次性加载海量数据 |

## 结论

`WHERE is_deleted = 0` 在数据量较小时不会暴露问题。当表规模增长后，缺少有效过滤条件的查询将直接拉崩服务。参数校验的核心价值在于阻断"条件坍塌为全表扫描"这条路径，而非满足数据库约束。
