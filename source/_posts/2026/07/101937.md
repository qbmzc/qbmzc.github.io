## 现象

`file-search` 服务所在节点磁盘使用率逼近 100%，但 `/tmp` 目录下未发现对应的大文件。`df -h` 与 `du -sh /tmp` 结果严重不符，差值持续累积。

## 定位

执行 `lsof +L1` 列出所有链接数（NLINK）为 0 但仍被进程打开的文件，发现数百个状态为 `(deleted)` 的 PDF 被 Java 进程持有：

```
java  11 root *504r  REG  0,268  3326098  0  7545173 /tmp/c6ebf8d790e547e8a7b86ee7564b4062.pdf (deleted)
java  11 root *505r  REG  0,268  3110127  0  7545174 /tmp/5e17f8f23c3244d090bbf2aa770fff2e.pdf (deleted)
```

- **FD 数量**：数百且持续增长
- **单文件大小**：数十 KB 至数十 MB
- **累计占用**：可达数十 GB

`(deleted)` 标记表明文件已被 `unlink`，但进程仍持有其文件描述符，磁盘空间尚未回收。

## 根因分析

### 调用链

`FileEsServiceImpl.buildIndexRequest()` 下载文件后交由 `fileContentReader.read()` 解析，并在 `finally` 中删除临时文件：

```java
try {
    localPath = downloadFile(fileInfo);
    fileContent = fileContentReader.read(
        new FileContentReader.ReaderContext(localPath, fileInfo, fileEsTask));
} finally {
    if (localPath != null) {
        FileUtils.delete(new File(localPath)); // unlink，但底层 FD 未释放
    }
}
```

`finally` 中的 `FileUtils.delete()` 执行了 `unlink`，从目录项移除了文件，因此 `ls /tmp` 不可见。

### 泄漏点

`PdfFileContentReader.read()` 解析扫描件 PDF（文本提取为空）时，会调用 `PdfCheckUtil.getNumberOfPages()` 判断文件是否损坏。该方法创建 `PdfReader` 后**未调用 `close()`**，导致底层 `RandomAccessFile` 句柄持续持有：

```java
// 修复前
PdfReader reader = new PdfReader(file);  // 打开 RandomAccessFile
int pages = reader.getNumberOfPages();
// reader.close() 缺失
```

### 为何空间未回收

在 Linux 中，`unlink` 仅移除目录项（dentry），并不立即释放磁盘块。**只有当该文件的所有打开文件描述符均关闭后，inode 及其数据块才会被回收。** `FileUtils.delete()` 完成了 `unlink`，但 `PdfReader` 持有的 `RandomAccessFile` 句柄未被关闭，进程仍占用该文件。由此产生的磁盘空间成为不可见的孤儿 inode，直至进程退出才归还。

## 修复

`PdfCheckUtil.java` 中创建 `PdfReader` 的两个方法（`getNumberOfPages()` 与 `isValid()`）均补充 `finally` 关闭逻辑：

```java
PdfReader reader = null;
try {
    reader = new PdfReader(file);
    pages = reader.getNumberOfPages();
} finally {
    closeReader(reader);
}

private static void closeReader(PdfReader reader) {
    if (reader != null) {
        try {
            reader.close();
        } catch (Exception e) {
            log.warn("close pdf reader err", e);
        }
    }
}
```

## 影响范围

| 项 | 说明 |
|----|------|
| 涉及文件 | `src/main/java/com/taimei/paas/filesearch/utils/PdfCheckUtil.java` |
| 触发条件 | 扫描件 PDF（OCR 文本为空），解析时调用 `getNumberOfPages()` |
| 复现频率 | 每份扫描件 PDF 的检索请求泄漏一个 FD，进程重启前不释放 |
| 积累速度 | 检索量较高时可在数小时内耗尽磁盘 |

## 应急恢复

```bash
# 统计被持有的孤儿文件总大小
lsof +L1 | awk '$5 == "REG" && $7 ~ /^[0-9]+$/ {sum+=$7} END {printf "%.2f MB\n", sum/1024/1024}'

# 重启进程以释放全部 FD（临时止血，根因需代码修复）
systemctl restart file-search
```

## 结论

`unlink` 与 FD 释放是两个独立动作：删除文件不意味着释放其占用的磁盘空间。对于非 try-with-resources 友好的资源（如 iText 的 `PdfReader`），必须在 `finally` 中显式关闭，否则将因孤儿 inode 累积导致磁盘静默耗尽。排查"磁盘满但无大文件"类问题时，`lsof +L1` 是定位持有已删除文件进程的首选手段。
