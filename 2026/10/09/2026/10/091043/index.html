Herdr + Whip ：让 Mac 和 Android 无缝接力 AI 编程任务

  • 2026-10-09
  • 作者 cong
  • ~10.18K 字

让 AI Agent 在远程服务器持续工作：电脑负责开发，手机负责监控和接管。告别 SSH 断线后任务中断的困扰。

关键词： Herdr、Whip、Android、Codex、OpenCode、SSH、WireGuard、AI Agent、远程开发

一、前言

最近一直在尝试将 AI Coding Agent 融入日常开发工作流。

目前常用的工具包括 Codex 和 OpenCode。它们已经能够完成代码生成、重构、测试、问题排查等任务，但在多设备协作方面，我一直有一个需求：

能不能在 Mac 上启动 AI 编程任务，离开电脑后通过 Android 手机继续查看和操作，回到电脑时又能直接接着工作？

传统 SSH 虽然能够实现远程操作，但并没有解决多 Agent 管理和移动端操作体验的问题。

经过研究，我选择了以下组合：

  • Herdr： 管理远程终端和 AI Coding Agent，提供持久化会话。

  • Whip： 专为 Herdr 设计的 Android/iOS SSH 客户端，提供原生 Agent 管理界面。

  • SSH： 连接电脑、手机与远程开发服务器。

  • WireGuard： 实现手机从外网安全访问内网服务器。

最终希望实现这样的效果：

  1. 在 Mac 上启动 Codex 编程任务。

  2. AI Agent 在远程服务器持续执行。

  3. 关闭 Mac 的 Herdr 客户端，任务依旧运行。

  4. 手机打开 Whip，查看 Agent 状态、阅读回复。

  5. Agent 需要输入时，直接在手机上继续对话。

  6. 返回 Mac，重新连接原来的任务和终端。

重点是：两个设备操作的是同一个远程 Herdr 会话，而不是各自运行一套 Agent。

二、整体架构设计

采用集中式运行架构，所有开发环境、代码和 Agent 都运行在远程 Linux 服务器上。

这里需要区分 Herdr 的 Server 和 Client。

Herdr Server 运行在远程服务器，持有终端和 Agent 的执行状态。Mac 本地的 Herdr 只是客户端，通过 SSH 连接远程 Server。

Whip 也是客户端，只不过它不是简单地将 Herdr 的终端界面搬到手机上，而是利用 Herdr 的接口，将 Agent 状态、会话管理和交互操作呈现为原生移动端界面。

这套架构的最大优势是：客户端可以断开，执行环境不需要跟着断开。

不过，持久化不等于永久执行。服务器宕机、Agent 自身退出、会话被停止等情况仍会影响任务运行。

  • 远程服务器已经安装并配置好 Codex 或 OpenCode。

  • Linux 服务器的 SSH 服务正常运行。

  • Mac 和 Android 都能够通过网络访问服务器。

  • 远程服务器上的 Herdr 版本与 Whip 支持的协议兼容。

本文假设 AI Agent 原本就在远程服务器运行，不涉及将本地项目迁移到远程服务器。

5.3 为什么推荐 herdr --remote

Herdr 提供两种常见的远程工作方式。

第一种：

此时 Herdr 的客户端和服务端都在远程 Linux 上运行，Mac 只是普通 SSH 终端。

第二种：

此时 Mac 负责 Herdr 界面的渲染，而终端及 Agent 仍保留在远程 Linux 服务器。

第二种方式更适合桌面日常开发，因为能够使用 Mac 本地的界面配置和部分桌面集成功能，例如图片剪贴板桥接。

两种方式都可以访问远程持久化会话。本文采用第二种。

场景四：网络中断

例如手机从 Wi-Fi 切换为 5G，SSH 连接可能短暂中断。

Whip 支持在应用恢复或网络变化后重新建立控制连接，尽量恢复对已有终端的访问。

不过需要区分三个概念：

  • 网络连接恢复：客户端重新连接服务器。

  • Herdr 会话持续：远程终端不因客户端断线而主动结束。

  • Agent 任务成功：仍取决于 Agent 自身、远程进程和服务器是否正常。

即使 Agent 的会话持续存在，也不能保证每次编程任务都执行成功。

9.2 Mac 能看到 Agent，Whip 却看不到

优先检查以下因素：

  1. 是否连接了同一台服务器。

  2. 是否使用同一个 Linux 用户。

  3. Session 名称是否一致。

  4. Herdr 是否正常运行。

  5. Whip 是否支持当前 Herdr 的协议版本。

特别是 Session 很容易配置不一致。

例如 Mac 连接 development，手机却连接 default，那么看到的就是不同会话。

9.3 手机端提示 Herdr 协议不兼容

Whip 并非 Herdr 官方项目，两者会独立更新。

不同版本之间可能存在协议兼容性限制。

遇到此类错误时，先查看：

再检查 Whip 的 About 页面显示的协议版本，以及其 GitHub README 的兼容说明。

不要直接假设升级到最新 Herdr 后旧版 Whip 就一定能够连接。

9.4 SSH 断开会停止 Agent 吗？

通常不会。

前提是 Agent 运行在 Herdr 管理的远程持久化 Pane 中，而不是在 Herdr 之外启动的普通 SSH 前台进程。

如果 Agent 是直接运行在普通 SSH Shell 内，那么连接中断仍可能导致进程退出。

因此，关键不是使用了 SSH，而是让任务真正运行在 Herdr 管理的会话内。

9.5 Whip 能否不打开就一直通知 Agent 状态？

Whip 支持 Agent 阻塞、完成等状态的本地提醒，以及可配置的通知和语音功能。

但不能将它简单理解为全天候云端推送服务。

通知是否及时取决于应用连接状态、后台运行权限、Android 电池优化策略等因素。

Whip 没有要求为此额外部署一个公网通知网关。

对于希望长期稳定监控任务的用户，仍应通过实际设备验证后台提醒行为。

十、安全建议

因为 Whip 可以直接操作远程终端和 AI Agent，所以必须把它视为具有服务器操作权限的客户端。

推荐的安全配置：

  • 使用 WireGuard 等私有网络访问服务器。

  • 为手机生成单独的 SSH 密钥，便于单独吊销权限。

  • 在首次连接时核对 SSH 主机指纹。

  • 不要将 SSH 私钥直接复制进项目仓库。

  • 避免让日常 Agent 使用 root 权限。

  • 对重要项目使用 Git 版本控制。

  • 为高风险操作保留人工确认。

  • 确保服务器有必要的备份和资源限制。

还需要注意，AI Agent 不一定只会修改代码。

如果 Agent 可以执行 Shell 命令，那么误操作可能影响文件、运行服务和其他数据。

移动端提供的是更方便的控制入口，并没有消除 Agent 本身的执行风险。

十一、这套方案的优势与不足

优势

1. 真正的多设备任务接力

Mac 和 Android 操作同一个远程运行环境，不需要重新创建 AI Agent 会话。

2. 远程资源集中管理

项目代码、依赖环境、API 凭据和 Agent 都位于远程服务器，终端设备只负责交互。

3. 不需要额外部署 Web 管理平台

Herdr 已具备持久化终端服务，Whip 直接通过 SSH 与其交互。

4. 充分利用现有设备

已有的 Linux 服务器、Mac 和 NAS 网络环境都能继续使用。

5. 手机端操作更自然

Whip 提供原生 Agent 管理、聊天、终端和文件浏览能力，比单纯在手机 SSH 中使用 TUI 更方便。

不足

1. 依赖远程服务器稳定性

服务器离线、磁盘不足或 Agent 进程异常，依然会影响任务。

2. 移动端与桌面端不是完全同步的 UI

共享的是服务器会话，而不是所有客户端界面状态。

3. Whip 与 Herdr 有兼容性要求

升级时需要关注接口协议变化。

4. 手机后台通知存在系统限制

不能保证所有 Android 设备都能够始终维持连接或及时提醒。
